# 0018: Review file changes before approval and after writing

**Status:** Accepted

## Context
The specification requires that changes generated by the agent be visible before they are
applied when relevant, and reviewable afterwards (accept, reject, revert, accept all, reject
all). Tools should stay simple and unaware of the UI.

## Decision
- **Before:** file-writing tools implement `proposedChange(arguments:context:)`, which computes
  the new content without writing. The executor turns it into a `FileDiff` shown in the
  approval banner. An edit that cannot apply fails immediately, without asking the user.
- **After:** the executor calls `FileChangeRecording.willModify` before each write. The
  `ChangeTracker` actor keeps the file's original bytes, once, from its first change. The
  Changes tab lists net changes with their diffs. Revert restores the original bytes exactly,
  or deletes a created file. Accept forgets the original.
- Diffs use the standard library's Myers implementation (`CollectionDifference`), grouped into
  hunks with 3 lines of context.

## Alternatives
- **Write to a staging area and apply on accept**: the agent's later tools (builds, tests)
  would not see its own changes.
- **Rely on Git for review**: fails outside repositories, and mixes the agent's changes with the
  user's own uncommitted work.

## Consequences
- The tracked originals are saved in SQLite (`changeOriginal`), so changes can still be
  reviewed and reverted after a relaunch. A storage failure is logged and tracking continues
  in memory.
- Changes made through `run_command` (e.g. a code formatter) are not tracked. Only
  `write_file`/`edit_file` are.
